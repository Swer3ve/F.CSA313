| ------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| Тойм               | Сервер гэнэт зогсоод (crash), 10 секундийн дараа дахин асахад системийн нийт бэлэн байдал хэрхэн хадгалагдахыг шалгах        |

| Гадаад өдөөлт      | Сервер процесс crash хийнэ (Omission → Crash төрлийн эвдрэл); 10 секундийн турш бүх хүсэлт `connection refused`              |
| Шаардлагатай хариу | Сервер дахин асаад л бүх 3 endpoint дахин хэвийн ажиллана; k6 клиент тал алдааг лог хийж, дараагийн хүсэлтээ илгээсээр байна |

## 2. SLO хүснэгт

| Сценарио             | SLI (юуг хэмжих)                       | Босго    | Цонх / нөхцөл                    |
| -------------------- | -------------------------------------- | -------- | -------------------------------- |
| Performance          | `/cart/add` latency p95                | < 200 мс | 20 VU тогтмол ачаалалд, 1 мин    |
| Performance (нэмэлт) | `/report` latency p95                  | < 450 мс | 20 VU тогтмол ачаалалд, 1 мин    |
| Reliability          | `/pay` error rate                      | < 8%     | 20 VU, 1 мин                     |
| Availability         | Бүх хүсэлтийн амжилтын хувь (`checks`) | ≥ 90%    | 2 мин, дунд нь 10с зогсолт орсон |

**Босго сонгосон үндэслэл:**

- `/cart/add` — синхрон, гадаад хамаарлагүй тул 200мс маш өгөөмөр (bottleneck биш) босго; localhost дээр бодит p95 ~1мс тул тестийн "эрүүл мэнд"-ийг батлах шинжтэй.
- `/report` — сервер дотроо 200-400мс sleep хийдэг тул зохиомлоор 450мс-г "хэвийн" гэж тогтоов (сая шидэгдсэн `Math.random()`-ийн дээд хязгаараас арай сул).
- `/pay` — сервер код дотор `Math.random() < 0.05` буюу ~5% алдаа санаатай суулгасан тул 8% нь "хэвийн хэлбэлзлийг" зөвшөөрсөн бодит босго (цэвэр 5%-аас дээгүүр, санамсаргүй хэлбэлзлийг тэвчих зай).
- Availability 90% — 2 минутын цонхонд 10 секундийн crash-ийг "зөвшөөрөгдөх эвдрэл" гэж загварчилсан тул сонгов.

**Error budget тооцоо (цагаар):**
2 минут (120с) × (100% − 90%) = **12 секунд** — энэ бол SLO-гийн зөвшөөрдөг "эвдрэх эрх" цаг.

## 3. k6 threshold код

`slo-test.js`:

```js
export const options = {
  vus: 20,
  duration: "1m",
  thresholds: {
    "http_req_duration{name:cart}": ["p(95)<200"],
    "http_req_duration{name:report}": ["p(95)<450"],
    "http_req_failed{name:pay}": ["rate<0.08"],
    checks: ["rate>0.90"],
  },
};
```

## 4. PASS үр дүн (`results/pass.txt`)

Хэвийн нөхцөлд (сервер тасалдаагүй) 20 VU, 1 минут:

- `{ name:cart }` p95 = **715.62 мкс (0.72мс)** → threshold p95<200мс: **PASS**
- `{ name:report }` p95 = **400.58 мс** → threshold p95<450мс: **PASS**
- `{ name:pay }` алдааны хувь = **3.13%** (29/924) → threshold rate<0.08: **PASS**
- `checks` = **98.95%** (2743/2772) → threshold rate>0.90: **PASS**

Бүх 4 threshold ✓ (PASS).

## 5. Chaos туршилт (`results/chaos.txt`)

2 минутын турш (20 VU) ажиллаж байх зуур ~40 секундийн үед сервер `SIGTERM`-ээр зогсоож, 10 секунд хүлээгээд дахин асаав.

- `checks` = **87.48%** (4971 / 5682) → threshold rate>0.90: **FAIL**
- `{ name:pay }` алдааны хувь = **15.52%** (294/1894) → threshold rate<0.08: **FAIL**
- `{ name:cart }` p95 = 770.12µs, `{ name:report }` p95 = 392.74мс — хоёулаа threshold-ынхаа дотор **PASS** хэвээр (эдгээр нь latency дээр суурилдаг тул connection-refused алдаатай хүсэлт latency тооллогод огт ордоггүй).

**Бодит availability тооцоо (хүсэлтээр):** 4971/5682 ≈ **87.48%** амжилттай (алдааны хувь 12.51%).

**Цаг ба хүсэлтийн зөрүү:** Алхам 3-т цагаар тооцсон budget 12 секунд (2 мин × 10%) байсан бол бодит зогсолт ~10 секунд — цагаар харвал budget-ийн дотор. Гэвч хүсэлтээр тооцвол алдааны хувь 12.51%, буюу budget (10%)-аас арай их гарсан. Учир нь сервер унасан үед `connection refused` хариу millisecond-ийн дотор буцдаг тул нэг "унасан" секундэд хэвийн үеийнхээс (нэг хүсэлт ~300-400мс) хавьгүй олон хүсэлт багтаж, тэдгээр БҮГД алдаатай тооцогддог — жижиг цагийн зогсолт хүсэлтийн тоогоор өсгөгдөнгүй "томорч" харагддаг.

**Reliability threshold мөн FAIL болсон шалтгаан:** Сервер унасан үед `/pay`-д илгээсэн хүсэлт бүр `connection refused` буюу алдаа болж тооцогддог тул нэг availability-ийн эвдрэл `checks` болон `http_req_failed{name:pay}` хоёр SLI-г ЗЭРЭГ зөрчинэ. Эдгээрийг тусгаарлахын тулд reliability SLI-г зөвхөн серверийн `200/500` хариунаас гаргаж, `connection refused` (network-level) алдааг тусад нь availability SLI рүү ангилах хэрэгтэй.

## 6. Зориудаар эвдэлсэн туршилт (`results/fail.txt`, `slo-test-fail.js`)

`/report`-ийн threshold-ыг `p(95)<100` болгож (сервер 200мс-с хурдан хэзээ ч хариулдаггүй тул найдвартай FAIL):

`{ name:report }` p95 = **401.16 мс** → threshold p95<100мс: **FAIL** (бусад бүх threshold — cart p95=795.79µs, pay error rate=4.30% (40/929), checks=98.56% (2747/2787) — PASS хэвээр, зөвхөн report threshold зориуд эвдэрсэн).

```
ERRO[0061] thresholds on metrics 'http_req_duration{name:report}' have been crossed
exit=99
```

k6 threshold зөрөхөд **exit code 99** буцаадаг — CI pipeline яг энэ кодоор build-ийг зогсоодог.

## 7. Дүгнэлт

Энэ лабораторид Лекц 3-ын "сценарио → SLO → threshold" гурван хэлний нэг санааг бүтнээр нь дадлагажуулав. Хамгийн хэцүү хэсэг нь сценариогийн "Хэмжүүр"-ийг зөвхөн тоо биш, тодорхой ачаалал, цонх, нөхцөлтэй хамт бичих байсан — учир нь тусгайлан заагаагүй бол хамгийн наад захын тоо ч утга учиргүй болдог. Мөн README-д бичсэн тоо, `slo-test.js` доторх threshold, `results/`-ийн бодит гаралтын тоо гурав нь бүгд адилхан байхыг баталгаажуулах нь давхар шалгалт шаардсан. Chaos туршилт availability сценариог хэсэгчлэн баталсан ч, цаг дээр суурилсан error budget тооцоо болон k6-ийн хүсэлт дээр суурилсан `checks` хэмжигдэхүүн хоёр өөр өнцгөөс ижил эвдрэлийг хэмждэгийг илрүүлж, миний анхны SLO хэт өөдрөг байсныг харуулав. Мөн availability ба reliability SLI хоёрын хооронд давхцал байдгийг харснаар, цаашид эдгээрийг network-error/application-error гэж ялгаж тодорхойлох хэрэгтэйг ойлгов. Threshold-ыг зориудаар эвдэхэд k6 яг тодорхой exit code (99) буцааж, энэ нь CI pipeline-д автомат шийдвэр гаргах үндэс болохыг харав. `/pay`-ийн алдааны хувь болон бусад p95 үзүүлэлтүүд `Math.random()`-той холбоотойгоор ажиллуулах бүрдээ бага зэрэг өөрчлөгддөгийг ажигласан тул README-дээ зөвхөн хамгийн сүүлд ажиллуулж, commit хийсэн run-ийхаа тоог тусгах ёстойг ойлгов — өмнөх run-ы тоог үлдээвэл README өөрөө "нотолгоогүй мэдэгдэл" болж хувирна. Мөн дэлгэц дээр харагдсан гаралт файлд хадгалагдаагүй бол ямар ч ач холбогдолгүй болохыг мэдэрсэн тул цаашид `Tee-Object`-оор шууд файлд бичихийг дадал болгохоор шийдэв. Нийтдээ, "README бол мэдэгдэл, нотолгоо бол ажилладаг код ба файл" гэдэг зарчмыг би энэ лабораторид бүх алхамдаа баримталж, тоо бүрээ `results/`-ийн бодит гаралттай тулгаж бичсэн.
